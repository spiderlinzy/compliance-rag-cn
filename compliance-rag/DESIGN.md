# 开发逻辑与架构设计

这份文档讲清楚系统是怎么一步步搭起来的、每个模块为什么这么设计。读完它，你应该能独立向别人解释整条信任链，甚至自己重做一遍。

## 一、先想清楚要解决的问题

普通问答里，模型直接生成、错了也没人查。金融合规场景要的是另一种东西：**每一句结论都要能被独立核查，查不到依据就宁可不说。** 所以整个系统围绕一个核心问题组织——怎么让模型的输出"可信、可追溯、可审计"。

答案是一条带多重防线的链，而不是指望某一个模型自觉：

```
问题 → 输入校验 → 检索（硬拦截）→ 生成（语义判断）→ 独立验证（结构+语义）→ 分层输出
```

每一道防线只负责自己最擅长的判断，任何一道不过就拒答，绝不带着疑点往下走。

## 二、先分清两个阶段：离线备料 vs 运行时问答

这是最容易混淆的一点。

- **离线备料（一次性）**：`build_docs.py` 把网页抓下来清洗成 md，`corpus.py` 把 md 切成片段。这些在程序启动时做一次，之后所有问答都复用，不会每问一句就重新抓取、切分。
- **运行时问答（每次提问都走）**：从问题进来开始，走"校验 → 检索 → 生成 → 验证 → 输出"这条链。

类比餐厅：备菜是早上一次性完成的，顾客点单时直接下锅，不会再从买菜开始。

## 三、各模块的设计逻辑

### 1. build_docs.py：抓取与清洗

- 顶部一张 `SOURCES` 表就近存放每个官网的网址、正文容器选择器和元数据，抓取逻辑只写一遍、循环处理。
- `requests` 负责"拿"网页，`BeautifulSoup` 负责"拆"标签。正文容器就是装正文的那个 HTML 盒子，要避开导航、广告等无关盒子。
- 清洗不追求洁癖：个别碎行、多余链接文字，只要下游能正确处理就接受。工程判断是**服务于下游、够用即可**，把精力留给检索—生成—验证这条信任链。

### 2. corpus.py：切分与自包含

切分用两层：

- **先按材料自身结构切**（法条按"第 X 条"、政策按大节、问答按"问："），好处是每个片段天然带人类可读的定位、语义完整不被砍断。
- **再用固定窗口处理超长块**：窗口 450 字、重叠 60 字（步长 390），重叠防止边界处语义被切断。

每个 Chunk 是**内存里的自包含对象**（不是硬盘上的小文件），自带编号、正文、来源、层级、定位等字段，流转到任何环节都不用再回头查原始文件。硬盘上始终只有 4 个完整 md。

### 3. retriever.py：BM25 检索与硬拦截

BM25 是关键词检索，比较问题和片段的词，不理解语义，两个关键机制：

- **逆文档频率（IDF）**：稀有词（如"敏感"）区分度高、权重高；到处都有的通用词（如"信息"）权重低。
- **词频饱和**：一个词出现一两次加分明显，出现很多次后几乎不再加分，防止长片段靠字数霸榜。

同时过滤停用词和标点——它们不是语义内容，否则含大量问号的长问题会刷分、把真正相关的片段挤出窗口。

硬拦截是第一道防线，纯代码、零成本：实词零命中，或最高分低于 `RELEVANCE_CUTOFF=3.0`，就直接拒答，不调模型。要注意 BM25 分不是百分比、没有固定上限，这个阈值是经验值。

### 4. generator.py：生成与语义判断

- 先做输入校验：空、超长（超过 500 字）直接拦下。
- 提示词定下铁律：只能用给定材料、每条陈述必须引用片段 ID、不许编造 ID、材料不足就把 `answerable` 设为 false。
- **判断"能不能答"和"生成答案"在同一次调用里完成**，省一次成本。
- 输出结构化 JSON（`{"answerable": ..., "items": [{"claim", "citation_id"}]}`），而不是自由文本，因为下游用 `json.loads` 就能确定性取字段，不用从自然语言里猜。
- 温度用 0.1，压低随机性，让合规问答稳定、不发散。

### 5. verifier.py：独立验证器（系统核心）

**为什么必须独立**：让生成者自己查自己，会带着"维护自己刚说的话"的倾向，等于运动员兼裁判。独立验证器没有这个包袱，唯一任务是拿原文挑错。

两层核查、漏斗式组织：

- **结构核查（代码、零成本）**：引用 ID 是否真实存在于本次检索结果，先把凭空编造的 ID 拦掉。
- **语义核查（独立模型调用，温度 0.0）**：把"陈述 + 原文"配对，判断原文是否真的支持，抓"真条款配假话"或错误演绎。
- 一个 ID 都不存在的引用，没必要再为它调模型，所以结构核查放最前。
- 验证器若漏返回某条，**保守按不通过处理**，宁可拦下也不放过。

### 6. glossary.py：受控术语表（把隐性常识变成可审计知识）

法条只写"生物识别"这样的概括词，用户却会问"虹膜、指纹是不是敏感信息"。完全禁止推断，系统会僵化到答不了具体例子；放开让模型用常识，又会重新引入不可控的幻觉。

折中是把"术语的标准下位实例"这种定义性、无争议的归类，显式写成一张受控词表：

- 白名单逻辑：只放行表里明确列出的归类，没列的一律按原规则拒答，所以表小不会导致错误。
- 生成器和验证器看到同一份词表：前者据此作答，后者据此确认归类有依据、再核对原文，权力制衡仍然成立。
- 可增量、可审计：先做高频类别，每个归类都能在法律或国家标准中找到依据。

它和"放开让模型自由发挥"的本质区别：这里每一步推断都能指回一份确定、可检查的材料，而不是模型脑子里说不清的常识。

### 7. cli.py：编排与拒答分叉

cli 自己不干活，只按顺序调用模块，并处理四个拒答分叉：输入校验不过、硬拦截、模型判 `answerable=false`、验证后无通过条目。

这里刻意**不做自动重试循环**：用同样的检索结果重新生成，模型很可能再犯同样的错，还增加成本和复杂度。不通过就拒答或剔除，把重新提问交给人。

## 四、置信度：代码算，模型不打分

模型不产出置信度，因为它的主观判断不可靠。置信度由代码按引用片段的 FTH 层级计算：

- 四份材料按法律强度分 L1 法律（高）、L2 行政法规（中高）、L3 企业制度（中）、L4 非正式问答（低）。
- 聚合要区分两种情况：**同一个结论被多个片段支撑时取最高层级**（强来源已能支撑，弱来源只是佐证，不该把它拉低）；**答案包含多个不同结论时，整体取最低层级（木桶效应）**，最弱的环节决定整体可靠性。
- 工程上让生成器在生成时就把重复结论合并、只锚定到最强片段，于是通过验证的每条都代表一个不同结论，再取最低即可，无需额外的语义分组调用。
- 低信度材料不能覆盖高信度材料，这是一条不依赖模型、由代码刚性保证的规则。

## 五、关键设计取舍

- **BM25 而非向量库**：本地可跑、先建立可靠基线；检索模块可整体替换，不影响其他环节。
- **刚性规则交给代码，语义判断才交给模型**：能确定性判断的就不引入幻觉风险。
- **生成与验证分离**：用独立调用换权力制衡。
- **先把"可靠地拒"做扎实**：自动重试、多轮上下文等都留到吃透闭环之后再加。

## 六、之后可以往哪走（先吃透当前闭环再考虑）

向量检索替换 BM25、多轮对话、自动重试、接入更多来源、加上人工复核工作台，都是自然的扩展方向。但在理解这条最小信任链之前，不建议急于叠加新框架——核心始终是"怎么把大模型用好、并让它的输出可信"。
